# 项目审计

项目卡片状态行里的评分按钮（仪表盘图标 + 分数）是「项目审计」，点击后弹出详情。有深度分析结果时以代码质量为主。它用来快速判断一个仓库在代码质量、维护、文档与安全维度上留下了多少可观察的证据。它不是项目质量裁决，也不代表项目是否适合生产使用。

普通审计在构建时刷新；深度代码质量由每日 GitHub Actions 单独运行，详见 [深度代码质量](./code-quality.md)。两者都会缓存到 `src/generated/`，浏览器端不请求任何第三方接口。

## 数据来源

| 来源                                        | 用途                                                           |
| ------------------------------------------- | -------------------------------------------------------------- |
| `src/data/projects.ts`                      | 项目与 GitHub 仓库的对应关系                                   |
| `src/generated/repository-stats.json`       | Stars、Fork、语言、License、归档状态、最近提交与 90 天提交数   |
| GitHub Community Profile API                | README、License、贡献指南、行为准则、Issue/PR 模板、社区健康度 |
| GitHub Contents API                         | 仓库根目录、常见源码目录与 `.github` 目录内容                  |
| `repository-code-quality.json`              | 每日深度分析产生的复杂度、重复率、lint、密钥与漏洞指标         |
| [OpenSSF Scorecard](https://scorecard.dev/) | 有公开结果时作为安全维度分数                                   |

GitHub 请求会复用统计同步中的 `GITHUB_TOKEN`。没有 token、网络失败或触发限流时，审计会退回上一次成功写入的缓存，构建不会中断。

## 总分

有深度代码质量结果时，总分以代码质量为主，保留整数，范围 0–100：

```text
总分 = 代码质量 × 60% + 维护 × 15% + 文档 × 10% + 安全 × 15%
```

没有可分析的源码或深度分析尚未运行时，回退到工程信号评分：

```text
总分 = 维护 × 25% + 文档 × 20% + 工程 × 30% + 安全 × 25%
```

| 等级 | 分数 | 含义                                 |
| ---- | ---- | ------------------------------------ |
| A    | ≥ 90 | 四个维度都有较强的可观察信号         |
| B    | ≥ 75 | 整体较完整，可能有个别缺口           |
| C    | ≥ 60 | 基本可用，但存在明显可改进项         |
| D    | ≥ 40 | 工程信号偏少，使用前应自行评估       |
| F    | < 40 | 可观察信号很少，不代表项目一定不可用 |

评分按钮本身使用中性色，弹层顶部的总分颜色与等级一致：A 为绿色，B 为蓝色，C / D 为琥珀色，F 为红色。按钮上的数字始终是总分，点击后可以看到各维度分数和具体检查项。

## 维度

### 代码质量（有深度数据时 60%）

代码质量来自每日静态分析，涵盖复杂度、重复率、lint、密钥和依赖漏洞。完整算法、工具覆盖与局限见 [深度代码质量](./code-quality.md)。

没有深度数据时，该维度不参与评分，弹层会显示“未深度分析”，并回退到下面的工程信号。

### 维护（15% 或回退时 25%）

- 65% 来自维护状态：活跃 100、维护中 82、低频 55、停滞 18、已归档 0。
- 35% 来自最近 90 天提交数：≥ 20 次为 100，≥ 10 次为 88，≥ 3 次为 72，≥ 1 次为 55，0 次为 25。
- 没有提交频率数据时给 35 分，并在检查项中标记为未知。

### 文档（10% 或回退时 20%）

- 社区健康度 × 35%。
- README +20，License +15，贡献指南 +10，行为准则 +5，Issue 模板 +5，`docs/` 等文档目录 +10。

### 工程护栏（回退时 30%，有深度数据时仅展示）

| 信号                                                                                  | 分值 |
| ------------------------------------------------------------------------------------- | ---- |
| 测试目录或 `*.test.*` / `*.spec.*` 文件                                               | 22   |
| CI 配置或 `.github/workflows`                                                         | 22   |
| 依赖清单（`package.json`、`pyproject.toml`、`CMakeLists.txt`、`requirements.txt` 等） | 12   |
| lockfile                                                                              | 8    |
| lint / format 配置                                                                    | 8    |
| `docs/` 等文档目录                                                                    | 5    |
| Dockerfile / Compose                                                                  | 5    |
| examples / demo / samples                                                             | 5    |
| 常见源码目录（`src`、`lib`、`app`、`firmware` 等）                                    | 13   |

这些检查读取**仓库根目录**，并在发现 `src`、`lib`、`app`、`firmware` 等常见源码目录时再读取该目录的一层。更深层的构建文件或测试目录不会自动加分。深度代码质量数据可用时，这些工程护栏项只作为辅助信息，不再主导评分。

### 安全（15% 或回退时 25%）

- 有公开 OpenSSF Scorecard 时，安全分 = Scorecard 分数 × 10。
- 没有 Scorecard 时使用回退规则：License 25、SECURITY 声明 30、Dependabot 20、CI 15、lockfile 10。
- 因此大多数没有公开 Scorecard 的仓库，安全分会明显偏低。

## 启发式 AI 风险

审计弹层里的「启发式 AI 风险」是基于工程信号缺失程度的启发式标签，**不检测代码是否由 AI 生成**。它回答的是：这个仓库是否缺少常见的工程护栏，而不是断定作者使用了 AI。

- 起始分来自缺失的 README、文档目录、许可证、测试、CI、依赖清单、lockfile、lint 配置与较低的社区健康度。
- 非代码项目（没有依赖清单、语言不是编程语言、根目录没有源码文件）会降低测试与 CI 的权重。
- 已获得一定社区采用的仓库会减分：≥ 500 Stars 或 ≥ 50 Forks 减 25；≥ 100 Stars 或 ≥ 20 Forks 减 20；≥ 20 Stars 减 10。最近 90 天有 ≥ 3 次提交再减 5。
- 0–34 为低，35–69 为中，≥ 70 为高。已归档或数据不足的仓库显示「未知」，不做推断。
- 展开审计详情可以看到触发的具体原因。

这个标签会误伤没有测试或 CI 的科研代码、课程作业和文档型仓库。请把它当作排查入口，而不是结论。

## 置信度

| 置信度 | 条件                                                     |
| ------ | -------------------------------------------------------- |
| 高     | Community Profile、根目录内容与 OpenSSF Scorecard 都可用 |
| 中     | Community Profile 与根目录内容可用，但没有 Scorecard     |
| 低     | 至少一类 GitHub 信号不可用                               |

置信度只描述数据完整度，不描述项目好坏。

## 构建与缓存

```bash
pnpm sync:audits          # 联网同步审计
pnpm sync:audits:offline  # 只用缓存，清理已移除项目的审计
```

`pnpm build` 会先同步项目状态，再同步审计，最后执行 Astro 构建。深度代码质量不在构建里运行，由每日 GitHub Actions 更新缓存；`SKIP_GITHUB_SYNC=1` 会跳过网络请求并使用缓存：

```bash
SKIP_GITHUB_SYNC=1 pnpm build
```

同步结束会输出：

- **已更新**：本次成功获取 GitHub 信号并重新审计的仓库数。
- **缓存回退**：GitHub 信号不完整、沿用上一次审计的仓库数。
- **跳过**：不在待审计列表中的仓库数。
- **请求失败**：仓库级请求错误次数；单个仓库失败不会中止整体同步。

缓存文件随仓库提交，作为离线与部署失败时的兜底。没有 GitHub 仓库的项目不会生成审计，卡片上也不会显示评分按钮。

## 如何解读

1. 先看维护状态，再看总分；审计分不能替代维护状态。
2. 分数低时展开详情，确认是缺测试、缺 CI、缺文档，还是嵌套结构导致的漏检。
3. 不要把不同项目类型的分数直接比较：文档集合、课程作业和科研代码的可观察信号本来就不同。
4. 需要更完整的安全判断时，使用 [OpenSSF Scorecard](https://scorecard.dev/) 或人工审查。
